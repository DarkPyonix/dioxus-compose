Rust로 쓰는 네이티브 UI

UI는 Dioxus로 쓰고, 그리는 일은 Compose에게 맡깁니다.

dioxus-compose는 Rust 코드가 rsx!와 컴포넌트, 훅으로 화면을 기술하고, 미리 컴파일해 둔 Compose Multiplatform 렌더러가 그것을 그리는 GUI 스택입니다. 웹뷰를 품지 않고, JVM을 함께 배포하지도 않습니다.

시작하기 동작 원리

왜 만드는가

이 스택이 겨냥하는 것은 하루 종일 켜 두는 애플리케이션입니다. 늘 켜 두는 도구에서는 무게가 매시간 체감됩니다. 그런데 웹 기반 셸은 가볍지 않습니다. 웹뷰는 브라우저 엔진을 통째로 데려오고, JRE는 jlink로 줄여도 80~120 MB가 붙습니다.

그렇다고 순수 Rust UI 프레임워크로 가면, 텍스트를 다루는 앱에서 가장 중요한 부분인 텍스트 자체에서 막힙니다. 한국어·일본어·중국어 입력은 플랫폼 IME를 거치고, 90%만 맞는 IME는 결국 쓸 수 없는 앱입니다. Compose Multiplatform은 텍스트와 IME, 위젯 품질이 이미 성숙해 있습니다. 그래서 이 프로젝트는 딱 그 부분만 빌려 옵니다. 애플리케이션 코드는 Rust에 남고, Compose는 Rust가 보내는 UI 트리를 해석하는 인터프리터가 됩니다.

협상 불가 조건그래서 생기는 결과
웹뷰 금지WKWebView, WebView2, WebKitGTK를 쓰지 않습니다. Tauri와 wry도 마찬가지입니다.
JVM 동봉 금지데스크톱은 GraalVM native-image 공유 라이브러리로 배포하고, iOS는 Kotlin/Native로 만들 계획입니다.
수동 JNI·cinterop 금지경계 심(shim)은 전부 Rust 스키마에서 생성합니다.
UI 코드는 Rust에Kotlin은 렌더러의 구현 세부일 뿐, 기능을 작성하는 자리가 아닙니다.
Compose 수준의 텍스트·IMECompose의 플랫폼 텍스트 입력을 우회하는 경로를 만들지 않습니다.

코드는 이렇게 생겼습니다

저장소의 desktop_demo 예제를 줄인 것입니다. 위젯 이름은 Compose 그대로이고, 속성은 그것을 snake_case로 옮긴 Rust 표기입니다.

현재 상태

로드맵을 기능 목록처럼 포장하지 않고 있는 그대로 적습니다. 사람이 직접 써 본 플랫폼은 macOS 데스크톱뿐이고, 나머지는 CI가 빌드하고 스모크 테스트를 돌릴 뿐이어서 증명하는 것이 그만큼 적습니다. 계획으로 표시한 항목은 설계만 되어 있고 구현은 없습니다.

플랫폼상태방식
macOS 데스크톱 (arm64) 동작 Liberica NIK 25 Full로 native-image --shared 빌드한 렌더러를 Rust 바이너리가 링크합니다. 2026-09-21에 이 빌드에서 한글 IME 체크리스트와 VoiceOver를 사람이 확인했습니다.
Windows 데스크톱 (x64) 빌드와 기동 업스트림 GraalVM 25로 빌드하고 렌더러가 바뀔 때마다 스모크 테스트를 돌립니다. 창이 열리고, 그려지고, 깨끗이 닫히며 0을 반환합니다. 호스티드 러너는 클릭을 할 수 없으므로 포인터 입력은 검증되지 않았고, 사람이 직접 써 본 적도 없습니다.
Linux 데스크톱 (x64, arm64) 빌드와 기동 두 아키텍처 모두 CI에서 Xvfb 아래 빌드되고 헤드리스 기동 스모크 테스트를 통과합니다. 증명하는 것은 거기까지이고, 실제 Linux 데스크톱 세션에서 이 렌더러가 그린 적은 없습니다.
iOS 빌드와 기동 Kotlin/Native -produce static으로 같은 C 심볼을 내보냅니다. 프로토콜 코덱 테스트가 Kotlin/Native에서 돌고, 기기용과 시뮬레이터용 아카이브가 빌드되며, 시뮬레이터 스모크 테스트가 스크린샷을 찍습니다. XCFramework로 배포합니다.
Android 계획 Kotlin이 프로세스와 루프를 소유하고, Rust cdylib을 생성된 JNI 심으로 호출합니다. 양쪽 모두 arm64-v8a로 빌드되지만, 기기나 에뮬레이터에서 돌아간 적은 없습니다.
Web (wasm) 계획 Kotlin이 wasm linear memory를 소유하고 Rust가 그것을 import합니다. 배치 arena를 제자리에서 공유하므로 복사가 없고, 경계 호출은 코드젠으로 만든 JS forwarder를 거칩니다. Safari에서 약 12 ns로 실측했고 다른 엔진에서는 아직 재지 않았습니다.

기능별 상태

기능상태메모
위젯 어휘동작컴포저블 33개 전부에 렌더러 쪽 구현이 있습니다. 스키마는 닫혀 있어서 그 밖의 것은 스키마부터 넓혀야 합니다. 컴포저블 레퍼런스를 보세요.
이벤트와 동기 소비동작on_click, on_value_change, on_submit, on_focus_lost, event.consume()이 붙는 on_key_down, 그리고 on_change와 on_dismiss.
비제어 TextField동작편집 값과 조합 상태를 렌더러가 소유합니다.
Rust 스키마 → Kotlin 프로토콜 코드젠동작생성물이 낡으면 테스트가 실패합니다.
Modifier동작모든 위젯에 속성 열세 개: weight, fill, 고정 크기, dp 또는 역할로 주는 패딩, 배경, 역할이나 반지름으로 주는 모양, 테두리, 높이. Clickable은 와이어에는 있지만 타입이 붙은 프로퍼티가 없습니다.
디자인 시스템과 테마동작하나의 역할 기반 계약 뒤에 디자인 시스템 일곱 개가 있고, 통일하거나 호스트 플랫폼을 따르도록 고릅니다. 디자인 시스템을 보세요.
LazyColumn과 LazyRow 윈도잉동작렌더러가 범위를 요청하고 Host가 정확히 그 범위만 만듭니다. 목록과 스트리밍을 보세요.
내비게이션, 시트, 한 번 지나가는 메시지동작렌더러가 재 본 너비를 보고 바인지 레일인지 드로어인지 고르고, 시트가 어느 가장자리에서 들어올지도 같은 방식으로 정합니다.
창 크기 클래스동작use_window_size()가 compact, medium, expanded를 알려 주고 클래스가 바뀔 때만 컴포넌트를 깨웁니다.
직접 그리기동작Canvas가 DrawList 값을 받습니다. 같은 목록 둘은 아무것도 보내지 않습니다.
AppendText 스트리밍rsx! API 없음Host가 프레임당 한 건으로 모으고 렌더러가 적용합니다. rsx! 수준 API는 없고 Host::append_text는 프로토콜 node id를 받습니다.
서드파티 위젯 확장컴파일 시점만확장은 양쪽에 함께 빌드되는 Rust와 Kotlin 소스 쌍이고, LinearProgressIndicator가 그 예제입니다. 배포된 렌더러는 새 위젯을 불러올 수 없습니다.
