목록과 스트리밍

긴 목록과 스트리밍 텍스트

채팅 클라이언트는 아주 긴 목록에 토큰 단위로 도착하는 텍스트가 얹힌 화면입니다. 둘 다 명세는 상세하지만 아직 구현되지 않았습니다. 그래서 이 페이지는 대부분 설계 이야기이고, 그 사실을 분명히 표시해 두었습니다. 그리고 그 사이에 쓸 수 있는 방법도 한 절 있습니다.

상태

LazyColumn과 AppendText는 계획 단계입니다 (SPEC FR-8, FR-9 / 마일스톤 M4). 위젯 스키마에도, 프로토콜에도, 렌더러에도 없습니다. 아래에서 예시라고 표시한 코드는 현재 크레이트로 컴파일되지 않습니다.

지금 되는 것

데이터를 for로 돌면서 Column에 넣는 방식은 제대로 동작하고, 화면 한 장에 스크롤백을 조금 더한 수백 행 정도에는 충분합니다. 다만 가상화는 하지 않습니다. 모든 항목이 양쪽에서 실제 노드가 됩니다.

메시지 하나를 고치면 SetProp 한 건만 전송되고 형제 노드는 recomposition되지 않습니다. 바람이 아니라 테스트로 지키는 요구사항(FR-4)입니다. 즉 이 패턴의 비용은 갱신 경로가 아니라 노드 수입니다.

LazyColumn 윈도잉 계획

평범한 트리 diff로는 가상화를 유지할 수 없습니다. 렌더러가 존재를 알게 하려면 Host가 아직 만들지도 않은 항목을 기술해야 하기 때문입니다. 그래서 lazy 목록에서는 흐름을 뒤집습니다.

  1. Host가 전체 아이템 개수와 아이템별 안정적인 key를 알립니다.
  2. 렌더러가 보이는 범위를 정해 RangeRequested 이벤트로 요청합니다.
  3. Host는 그 범위와 버퍼만큼만 서브트리를 만듭니다.

수용 기준도 구체적입니다. 아이템 10,000개짜리 목록에서 생성되는 노드 수가 목록 길이가 아니라 가시 범위와 버퍼에 비례해야 합니다.

스트리밍 텍스트 계획

LLM 응답은 토큰 단위로 도착합니다. 토큰마다 text 속성을 통째로 갈아 끼우면 매번 메시지 전체를 다시 보내게 되고, 메시지는 계속 길어지므로 비용이 제곱으로 늘어납니다. 명세가 제시하는 답은 Text 노드의 AppendText 명령이고, Host가 프레임 주기(약 16 ms) 단위로 토큰을 모아 한 번에 붙입니다.

수용 기준은 초당 100토큰 스트리밍 중에도 스크롤과 입력이 끊기지 않는 것입니다.

그때까지는 시그널을 갱신해서 diff가 SetProp을 보내게 하는 방식으로 스트리밍할 수 있습니다. 짧은 응답에는 충분히 쓸 만하고, 긴 응답에서는 메시지 길이에 따라 프레임당 비용이 올라간다고 보면 됩니다.

워커 스레드에서 스트리밍하기

이 절은 계획이 아니라 지금의 규칙이고, 앞의 두 기능보다 중요합니다. 도메인 작업은 UI 스레드에서 돌면 안 됩니다. 그 스레드는 컴포넌트와 경계 전체가 함께 쓰는 스레드입니다. PTY 읽기, HTTP, LLM 스트리밍, 파일 I/O는 Host 워커 스레드의 일입니다.

UI 관점에서 워커가 할 일은 시그널에 쓰는 것뿐입니다. 렌더러를 깨우는 것은 내부 동작입니다. Host가 대신 프레임을 요청하고, 여러 번의 요청은 다음 Compose 프레임 클록 안에서 render_frame 한 번으로 합쳐집니다. 사용자 코드가 경계 함수를 부를 일도, 사이에 쌓여 넘칠 큐도 없습니다.

기억해 둘 결과 하나

핸들러는 렌더러가 Host를 호출한 그 안에서 돕니다. 그래서 핸들러 안에서 요청한 프레임은 그 호출이 끝날 때까지 미뤄집니다. 핸들러에서 렌더러로 다시 들어가는 것은 금지입니다. 상태만 바꾸고 프레임에 맡기세요.

프레임 예산

이 프로젝트의 성능 목표는 절대 수치가 아니라 비교입니다. 같은 화면을 Kotlin과 Compose로 직접 만든 것이 기준선이고, 이 스택은 그보다 프레임 시간이 10%까지만 더 들 수 있습니다. 코드 작성 방식에 영향을 주는 항목 몇 가지입니다.

항목기준 (p99, 릴리스)
Host 처리: 핸들러 + diff + 배치 인코딩일반 상호작용 ≤ 0.5 ms, 스트리밍 프레임 ≤ 1 ms
경계 호출 1회데스크톱·iOS ≤ 100 ns
렌더러의 배치 적용Mutation 100건당 ≤ 0.3 ms
입력 → 화면기준선과 같은 프레임 수. 추가 지연 0프레임
프레임 드랍1만 개 메시지 대화에서 초당 100토큰 스트리밍 + 스크롤 중 0

할당은 절대값이 아니라 추세로 봅니다. Dioxus는 diff와 이벤트 처리 과정에서 내부적으로 할당하고(2026-09-20 측정: 클릭당 99회), Rust에는 GC가 없어 이 할당이 멈춤으로 이어지지 않습니다. 중요한 것은 같은 상호작용을 반복해도 할당 수가 늘지 않는 것입니다. 늘어난다면 누수이거나 캐시가 동작하지 않는 것으로 보고 버그로 다룹니다.
