지금 되는 것

구현은 이 저장소의 코드와 그것을 실행하는 통과 테스트가 함께 있다는 뜻입니다. 부분은 일부가 있고, 어느 부분인지 이 페이지에 적었다는 뜻입니다. 계획은 설계했지만 만들지 않았다는 뜻입니다.

HTML 과 CSS 경로

상태항목
구현HTML 요소로 쓴 Dioxus 앱을 창 없는 blitz-dom 문서(HtmlDom)에서 실행하고, 스타일시트를 Stylo 로 풀기
구현레이아웃: 블록과 인라인 흐름, flexbox, grid, 표, position relative / absolute / fixed, z-index, min-width: fit-content, box-sizing
구현장식: 배경색, 변마다의 테두리, 모서리 반지름, box-shadow, opacity, visibility
구현overflow: 클리핑, 두 축 어느 쪽이든 스크롤 컨테이너
구현배경: 선형과 원형 그라디언트, 배경 이미지, object-fit. 앱이 넘기는 ImageResolver 를 거치며 아무것도 내려받지 않음
구현텍스트: 인라인 조각, white-space, text-transform, letter-spacing, 생성된 내용, 바꿔 끼울 수 있는 TextMeasurer
구현이벤트: 전파와 브라우저 기본 동작을 포함한 클릭, input / change / submit, select, 체크박스, 라디오 그룹, label, 비제어 입력란
구현키가 있는 목록, 바뀐 것만 알려 주는 그리기 목록 diff 와 계획 diff
구현사용자 정의 속성과 prefers-color-scheme 으로 테마 주기
구현<script> 를 실행하지 않음
구현VS Code 가 잰 텍스트 크기로 워크벤치 세 구역의 상자 326 개 중 324 개가 VS Code 와 1px 이내(dioxus-compose/tests/fr34_box_tolerance.rs, 2026-10-03 macOS 에서 측정)
구현samples/ 의 예제 열한 개. 각각 손으로 계산한 배치와, 렌더러가 부를 것과 같은 호출로 Host 에서 테스트됨
부분HTML 화면을 화면에 그리기. 다리가 계획을 compose-rust 의 배치(batch)에 씀. 첫 프레임에는 트리 전체, 그 뒤로는 계획 diff 가 알려 주는 것만 보내고, 바뀐 것이 없는 프레임은 아무것도 보내지 않음. 계획의 모든 종류가 compose-rust 위젯(AbsoluteBox, Box, Text, Image, 스크롤 행과 열, 입력란, 체크박스, 라디오 버튼, 드롭다운)이 되고, 렌더러의 이벤트는 Dioxus 핸들러에 닿음. 렌더러가 받는 레코드로 Host 에서 테스트했고, 화면에 그려지는 것은 아직 렌더러를 돌려 확인하지 않음(#43)
부분화면의 텍스트 스타일과 이미지 맞춤. compose-rust 의 Text 가 글꼴 패밀리와 기울임을 받지 않으므로 텍스트는 디자인 시스템의 글꼴로 그려지고, font-family, font-style, text-decoration 은 아직 화면에 닿지 않음. compose-rust 의 Image 는 그림을 통째로 가운데에 그리므로, 비율이 다른 object-fit: fill 은 여백을 두고 그려짐(#43)
부분Compose 로 텍스트 재기. 측정기는 글꼴이 하나인 텍스트를 재고, 글꼴이 섞인 문단, 표 칸, 입력 컨트롤은 Parley 가 잼. 동기 측정 호출은 compose-rust 에서 만드는 중(#43)
부분CSS 변환: translate 는 동작, rotate, scale, skew, matrix(), transform-origin 은 그리지 않음(#46)
계획CSS transition 과 animation: 불투명도, 변환, 색은 렌더러에서(#46), 폭, 높이, 여백은 Host 를 거쳐(#47)
부분HTML 화면에서 DOM 이벤트로서의 키와 포커스. Enter 는 포커스가 있는 요소에서부터 버블링하며 keydown 과 keypress 를 보내고, 입력 칸은 focus, blur, focusin, focusout 을 보냄. Host 에서 테스트함. compose-rust 가 실어 나르는 키는 Enter 하나이고 키를 뗀 것은 싣지 않아서 keyup 은 보내지 않음. 입력 칸이 포커스를 잃는 것은 알리지만 얻는 것은 알리지 않아서 focus 는 첫 입력과 함께 옴(#43)
부분실행 중의 밝은 테마와 어두운 테마. 앱이 테마를 밝게나 어둡게 바꾸면 prefers-color-scheme 이 따라가고, 스타일이 바뀐 상자만 보냄. 시스템의 변화는 렌더러가 적용하고 Host 에 알리지 않아서, 시스템을 따르는 테마에서는 설정한 색 구성표를 유지함(#43)
계획시스템 글자 크기에서 시작해 VS Code 처럼 HTML 화면 확대하기(#58)
계획한 화면에 HTML 과 위젯 함께 두기(두 방식 섞기)(#59)

Compose 위젯 경로

상태항목
구현위젯 목록, 모디파이어, 키 소비를 포함한 이벤트, 비제어 TextField
구현LazyColumn 과 LazyRow 창 단위 처리: 렌더러가 범위를 묻고 Host 는 그 범위만 만듦
구현역할 기반 계약 하나 뒤의 디자인 시스템 일곱 개, 통일 또는 호스트 플랫폼 따르기
부분스트리밍 텍스트: 덧붙인 꼬리를 프레임마다 모으지만 rsx! 수준 API 는 없음
계획마크다운 크레이트 dioxus-compose-markdown, 스트리밍을 포함해 마크다운을 위젯으로(#24)

위젯 경로의 플랫폼

렌더러와 그 빌드는 compose-rust 의 것입니다. 플랫폼마다 지금까지 보인 것은 다음과 같습니다.

플랫폼상태근거
macOS (arm64)구현한글 입력을 포함해 직접 써 봄. Java 런타임 없는 파일 하나
Android구현예제 앱이 에뮬레이터에서 돎
Web (wasm)구현브라우저에서 화면이 그려지고 클릭이 Rust 에 닿음
Windows, Linux부분CI 에서 빌드되고 시작됨. 직접 써 보지는 않음
iOS부분시뮬레이터 스모크 테스트에서 빌드되고 시작됨

FAQ

Dioxus 웹 앱을 그대로 가져올 수 있나요?
HTML 경로가 받는 것이 그 rsx! 와 CSS 이므로 화면은 배치되고 다리를 거쳐 렌더러로 갑니다(화면에 그려지는 것은 아직 확인하지 않았습니다, #43). 브라우저 API 나 JavaScript 를 부르는 부분은 여기에 대응하는 것이 없습니다.
JavaScript 를 실행하나요?
아니요. <script> 는 아무 일도 하지 않습니다. 동작은 Rust 로 씁니다.
어딘가에 웹뷰가 있나요?
아니요. CSS 는 Rust 에서 blitz-dom 이 계산하고, 그 결과를 Compose 가 그립니다.
crates.io 에 있나요?
0.0.0 이 위젯 경로만 있는 초기 스냅숏으로 있습니다. HTML 경로는 develop 브랜치에 있습니다. 시작하기를 보십시오.
Kotlin 을 알아야 하나요?
아니요. 렌더러는 compose-rust 를 거쳐 미리 빌드된 채로 오고, 코드는 Rust 만 씁니다.
