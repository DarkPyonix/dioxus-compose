The bridge writes the plan into compose-rust's batch: the whole tree on the first frame, then only what the plan diff reports, and nothing for an unchanged frame. Every plan kind becomes a compose-rust widget (AbsoluteBox, Box, Text, Image, scroll rows and columns, fields, checkboxes, radio buttons, dropdowns), and renderer events reach the Dioxus handlers. It is tested on the Host against the records the renderer receives; drawing on screen has not been confirmed by running the renderer yet (#43)

Text is drawn in the design system's typeface, because compose-rust's Text takes no font family or italic, so font-family, font-style and text-decoration do not reach the screen yet. object-fit: fill with a different aspect ratio is drawn letterboxed, because compose-rust's Image draws a picture whole and centred (#43)
partialText measured by Compose. Your measurer sizes single-font text; mixed fonts, table cells and form controls are measured by Parley. The synchronous measure call is being built in compose-rust (#43)
partialCSS transforms: translate works; rotate, scale, skew, matrix() and transform-origin are not drawn (#46)
plannedCSS transitions and animations: opacity, transforms and colours in the renderer (#46); width, height and margins through the Host (#47)
partialKeys and focus as DOM events on HTML screens. Enter delivers keydown and keypress, bubbling from the focused element, and a field delivers focus, blur, focusin and focusout; tested on the Host. Enter is the one key compose-rust carries and it has no key release, so keyup is never sent; it reports a field losing the focus but not gaining it, so focus arrives with the first keystroke (#43)
partialLight and dark while running. prefers-color-scheme follows the theme when the application switches it to light or dark, and only the boxes whose style changed are sent. A system change is applied by the renderer and not reported to the Host, so a theme that follows the system keeps the configured scheme (#43)
plannedZooming HTML screens the way VS Code does, starting from the system text size (#58)

FAQ

Can I bring my Dioxus web app?
Its rsx! and CSS are what the HTML path takes, so the screens lay out and reach the renderer through the bridge (drawing on screen is not yet confirmed, #43). Anything that calls browser APIs or JavaScript has no counterpart here.
Does it run JavaScript?
No. A <script> element is inert. Behaviour is written in Rust.
Is there a webview anywhere?
No. CSS is computed in Rust by blitz-dom, and Compose draws the result.
Is it on crates.io?
Version 0.0.0 is, as an early snapshot with the widget path only. The HTML path is on the develop branch; see Getting started.
Do I need Kotlin?
No. The renderer arrives prebuilt through compose-rust, and your code is Rust only.
