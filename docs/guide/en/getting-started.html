Getting started

From an empty crate to a laid-out page

This page adds the crate, writes a page with HTML and CSS, lays it out, clicks it and opens it in a window. The window goes through the renderer bridge, whose records are tested on the Host; what it draws has not been confirmed by running the renderer yet (#43).

Add the crate

The HTML path is on the develop branch and is not in a crates.io release yet. The 0.0.0 release on crates.io is an early snapshot with the widget path only. Depend on the repository for now:

dioxus-hooks and dioxus-signals give you use_signal and the signal traits, the way the examples use them. The first build also fetches the renderer, through compose-rust's build script. The widget path draws with it; HTML screens do not use it yet.

Write a page

A page is a component and a stylesheet. The examples keep both in one file and export them as app and STYLE, so a window can show the page and a test can lay it out without one.

The elements are Dioxus's own HTML elements, the same ones a web or desktop Dioxus app uses. The attribute is class, events are onclick and oninput, and event.prevent_default() works as it does on the web.

Lay it out

HtmlDom runs the app and lays it out at a viewport size in CSS pixels and a scale in device pixels per CSS pixel. The display list it returns has one entry per box, in paint order.

cargo run prints the boxes and exits. Open it in a window shows the main that hands the page to the renderer instead. HtmlConfig also takes a text measurer, a colour scheme, a base URL and an image resolver, which the following pages cover.

Click it

A click at a point goes to the handler of the element under it, the way a pointer event from the renderer does. This is the hello example's own test, trimmed. The numbers come from its stylesheet and a test measurer that makes every character half the font size wide.

Handlers run during click. render applies what they changed to the document, and the next layout shows it.

Open it in a window

An HTML app is launched the way a widget app is. LaunchBuilder::with_html takes a function that returns the HtmlConfig, because the Host makes a fresh document each time the renderer asks for the whole tree again.

dioxus_compose::html::launch(app) does the same with the default configuration. In a checkout of this repository, cargo run -p sample-html-hello opens the hello example this way; it is the only example with a desktop binary so far. On Android and in the browser the entry macros take the same builder as their first argument, for example android_main!(LaunchBuilder::new().with_html(config), app), and web_main! likewise; on iOS ios_main!(launch) calls the same launch. The hello sample declares all three, so it builds for each platform the native-widget samples do. The page sits in a vertical scroll the size of the window, and clicks, typed text, form controls, Enter (onkeydown, onkeypress) and a field's focus reach your handlers through the bridge. Other keys and onkeyup do not, because Enter key presses are all compose-rust carries, and text is drawn in the design system's typeface rather than the stylesheet's font-family. The bridge is tested on the Host and drawing on screen is not yet confirmed (#43).

Run the examples

Eleven examples in samples/ are written this way, one crate each, and the rest of this guide quotes them. Their tests check every layout against numbers worked out by hand, and click, type and submit through the same calls a renderer makes. In a checkout of the repository:

The widget path, which draws today

An app written with Compose widget names runs in a window now, with the same dependency. dioxus_compose::launch(app) opens the window, and cargo run builds and starts it. The renderer comes from compose-rust, whose build script downloads the one for your target. See Widgets in rsx! for how those apps are written, and samples/native-widgets/ for examples.

Working on this repository

Everything here is Rust, so the tests are one command:

./scripts/check.sh is the full gate: formatting, Clippy with warnings denied, the tests and the benchmarks. The renderer, its build and the design systems live in compose-rust, and its README covers working on them.
