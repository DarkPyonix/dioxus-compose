Getting started

From a clean checkout to a window on screen

Using the crate is one line in a Cargo.toml: the build downloads the renderer it needs. Working on the renderer itself is the longer path below.

Adding it to a project

The renderer is a shared library your binary links against, and it is far too large for crates.io, so it ships as a checksummed artifact on the release for each version. Fetching it is the build script's job, not yours:

cargo build works out which renderer this target needs, downloads the artifact for the crate's exact version, checks it against the published .sha256, unpacks it into a cache outside target/ and links it. The cache is keyed by version and target, so it survives cargo clean and is shared between projects on the machine. Nothing else to set, fetch or run.

Two variables exist for the cases that need them, and neither is part of installing. DIOXUS_COMPOSE_RENDERER_DIR points at a renderer you already have, and is checked before anything is downloaded, so a renderer you built yourself, a vendored copy or an air-gapped build all work through it. DIOXUS_COMPOSE_CACHE_DIR moves the cache. A build with no network tells you which two files to put where, and putting them there is all it takes.

Building without a renderer

default-features = false gives you the Host with no renderer at all, which is what a headless or documentation build wants. Running a binary built that way prints what is missing and exits non-zero. It does not open no window and return 0: a program that drew nothing has to be distinguishable from one that finished its work.

Everything below is about working on this repository, which needs the renderer toolchain as well.

Prerequisites

Before anything else, run ./scripts/setup-check.sh. It checks every tool the build and the quality gate need, names what is missing, and prints the command that fixes it. Everything in the table below is on its list.

The renderer resolves Compose from your local Maven repository, not from what JetBrains published. Three things this project needs are empty in the published build for this platform, and none of them can be filled from outside the module that holds them: the entries a text selection's menu offers, the keys that copy, and the Linux targets. The patches are in dioxus-compose-renderer/patches/, pinned to one Compose revision, and each says what it is for.

It fetches the pinned revision, applies the patches, and publishes the modules the renderer asks for. This is slow and you run it once, not once per build. Everything else still resolves from what JetBrains published.

If you do build the native image, use Liberica NIK

Upstream GraalVM skips AWT support on Darwin (oracle/graal#13272, still open as of 2026-09), and the native image draws through AWT, so an image built with upstream GraalVM has no window to show. Liberica NIK Full links AWT statically. This does not apply to the renderer macOS ships, which is Kotlin/Native and links no AWT at all: the native image is how Windows is built and what desktop/scripts/smoke-test.sh links against.

The build script looks for NIK in the standard install location and otherwise reads GRAALVM_HOME:

If you have no NIK at all, ./scripts/install-nik.sh installs it. The install is addressed by version, so a warm cache makes a second run a no-op, the download happens once per NIK version, not once per invocation. The native-image build itself refuses an installation without lib/static/darwin-*/libawt_lwawt.a, which catches a stock GraalVM up front instead of at the end of a long build.

Kotlin itself needs no separate install. The renderer project ships a self-bootstrapping ./kotlin wrapper that downloads the pinned Kotlin Toolchain on first use.

Build the renderer

On macOS one script does the whole thing. It compiles the renderer as a Kotlin/Native static library, with Compose, Skia and the interpreter inside it:

The result is one archive and the header generated for it:

Nothing is installed beside it. The linker folds the archive into your executable, so what you ship is a single file with no runtime directory and nothing loaded by file path. The two symbols the Host calls, dioxus_compose_renderer_run and dioxus_compose_renderer_request_frame, have the same names and signatures on every platform.

Windows has no Kotlin/Native target that can be linked against Skia, so it is built as a GraalVM native image instead, by build-native.sh on a Unix host and build-native-windows.ps1 on Windows. That build carries a Java runtime, and its output is a lib/ directory rather than one file, because statically linked AWT still resolves some things by path at runtime.

In a checkout of this repository the Rust build prefers the renderer you just built over anything it could download. The full order is DIOXUS_COMPOSE_RENDERER_DIR, then this workspace build, then the cache, then the release for the crate's version (NFR-10).

The first build is slow: Compose and Skia are compiled ahead of time. You only repeat it when the Kotlin side changes; normal Rust work reuses the library.

Run the demo

The desktop example asks for the native-renderer feature explicitly, which is what an example that needs a window has to do. It is on by default for an ordinary build:

Type a message and press Enter to send it, or Shift+Enter for a newline. If you use a Korean, Japanese or Chinese IME, press Enter while a syllable is still composing: it should commit the composition and not send the message. That distinction is the point of the whole design and is covered in Writing UI.

The Host without a window

The unit tests and the benchmarks drive the Host directly, with no renderer and no window, and the mock-renderer feature is how an embedder asks for the same thing. Those builds are silent by design. A build that simply has no renderer is not: it says so and exits non-zero.

Run the checks

The repository's quality gates are one script: formatting, Clippy with warnings denied, the test suite, the benchmarks in Criterion's quick mode, and the Kotlin build and tests.

One of those tests compares the checked-in Kotlin protocol file against what the Rust schema generates. If you change the schema and forget to regenerate, the test fails, which is the intended behaviour, not an inconvenience.
