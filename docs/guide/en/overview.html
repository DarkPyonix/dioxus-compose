Native UI, written in Rust

Author your UI with Dioxus. Let Compose draw it.

dioxus-compose is a GUI stack in which Rust code describes the interface with rsx!, components and hooks, and an ahead-of-time compiled Compose Multiplatform renderer paints it. No webview is embedded, and no JVM ships with your application.

Get started How it works

Why it exists

This stack is aimed at applications that stay open all day, where weight is felt every hour. Web-based shells are not light: a webview brings a browser engine with it, and a bundled JRE adds 80 to 120 MB even after jlink.

The obvious answer, a pure-Rust UI framework, fails on the part that matters most for anything text-driven: text itself. Korean, Japanese and Chinese input goes through the platform IME, and an IME that is 90% right is an app you cannot use. Compose Multiplatform already has mature text, IME and widget behaviour, so this project borrows exactly that and nothing else: Rust keeps the application code, Compose becomes an interpreter for a UI tree that Rust sends it.

ConstraintConsequence
No webviewNo WKWebView, WebView2 or WebKitGTK; no Tauri, no wry.
No bundled JVMDesktop ships as a GraalVM native-image shared library; iOS as a Kotlin/Native static archive.
No hand-written JNI or cinteropEvery boundary shim is generated from the Rust schema.
UI code lives in RustKotlin is an implementation detail of the renderer, not a place you write features.
Compose-quality text and IMENo code path may bypass Compose's platform text input.

Status

This is an honest table, not a roadmap dressed as a feature list. macOS desktop is the platform that has been used by hand; the others are built and smoke-tested by CI, which proves rather less. Everything marked planned is designed and not implemented.

PlatformStatusHow it is meant to work
macOS desktop (arm64) Works Renderer built with GraalVM native-image --shared on Liberica NIK 25 Full; the Rust binary links it. The Korean IME checklist and VoiceOver were confirmed by hand on this build on 2026-09-21.
Windows desktop (x64) Builds and starts Built with upstream GraalVM 25 and smoke-tested on every renderer change: the window opens, draws, closes cleanly and returns 0. A hosted runner cannot click, so pointer input is unproven there, and nobody has used it interactively.
Linux desktop (x64 and arm64) Builds and starts Both architectures build under Xvfb in CI and pass a headless startup smoke test. That is all it proves: no Linux desktop session has drawn this renderer.
iOS Builds and starts Kotlin/Native -produce static exporting the same C symbols. The protocol codec tests run on Kotlin/Native, the device and simulator archives build, and a simulator smoke test takes a screenshot. Released as an XCFramework.
Android Planned Kotlin owns the process and the loop; Rust is a cdylib reached through generated JNI shims. Both halves build for arm64-v8a, and nothing has run on a device or an emulator.
Web (wasm) Planned Kotlin owns the wasm linear memory and Rust imports it, so the batch arena is shared in place with no copying. Each boundary call goes through a generated JS forwarder, measured at about 12 ns in Safari and not yet re-measured elsewhere.

Feature status

FeatureStatusNotes
The widget vocabularyWorksThirty-three composables, with a renderer half for every one of them. The schema is closed: anything else has to be added to it first. See the composable reference.
Events and synchronous consumptionWorkson_click, on_value_change, on_submit, on_focus_lost, on_key_down with event.consume(), on_change and on_dismiss.
Uncontrolled TextFieldWorksEdit and composition state live in the renderer.
Kotlin protocol codegen from the Rust schemaWorksA stale Kotlin file fails the test suite.
ModifiersWorksThirteen attributes on every widget: weight, fill, explicit size, padding in dp or by role, background, shape by role or radius, border and elevation. Clickable is on the wire but has no typed prop.
Design systems and themingWorksSeven design systems behind one role-based contract, chosen unified or following the host platform. See Design systems.
LazyColumn and LazyRow windowingWorksThe renderer asks for a range, the Host materialises exactly that range. See Lists & streaming.
Navigation, sheets and transient messagesWorksThe renderer picks bar, rail or drawer from the width it measured, and the same for which edge a sheet enters from.
Window size classesWorksuse_window_size() reports compact, medium or expanded, and only wakes a component when the class changes.
Custom drawingWorksCanvas takes a DrawList value. Two equal lists send nothing.
AppendText streamingNo rsx! APICoalesced per frame by the Host and applied by the renderer. There is no rsx!-level API: Host::append_text takes a protocol node id.
Third-party widget extensionCompile time onlyAn extension is a Rust and Kotlin source pair built into both sides, with LinearProgressIndicator as the worked example. A deployed renderer cannot load a new widget.
