Lists & streaming

Long lists and streaming text

A chat client is a very long list plus text that arrives a token at a time. Both are specified in detail and neither is implemented yet, so this page is mostly design — clearly marked as such — with one section on what you can build in the meantime.

Status

LazyColumn and AppendText are planned (SPEC FR-8 and FR-9, milestone M4). They are not in the widget schema, not in the protocol and not in the renderer. The code on this page marked illustrative will not compile against the crate as it stands.

What works today

A Column with a for loop over your data renders correctly and is fine for the hundreds of rows that fit an ordinary screen with some scrollback. It does not virtualise: every item becomes a real node on both sides.

Updating one message sends exactly one SetProp mutation, and sibling nodes are not recomposed — that is a tested requirement (FR-4), not an aspiration. So the cost of this pattern is the node count, not the update path.

LazyColumn windowing Planned

A plain tree diff cannot keep a virtualised list virtual: the Host would have to describe items it has never built in order for the renderer to know they exist. The design therefore inverts the flow for lazy lists.

  1. The Host declares the total item count and a stable key per item.
  2. The renderer decides which range is visible and asks for it with a RangeRequested event.
  3. The Host builds subtrees only for that range plus a buffer.

The acceptance criterion is concrete: with 10,000 items, the number of created nodes stays proportional to the visible range and its buffer, not to the list length.

Streaming text Planned

An LLM response arrives token by token. Replacing the whole text property on every token would re-send the entire message for each one, and the message grows, so the cost grows quadratically. The specified answer is an AppendText command on a Text node, with the Host coalescing tokens into one append per frame (roughly 16 ms).

The acceptance criterion: at 100 tokens per second, scrolling and typing stay smooth.

Until it exists, stream by updating a signal and letting the diff send a SetProp. For a short answer this is perfectly usable; for a long one, expect the per-frame cost to climb with the length of the message.

Streaming from a worker thread

This part is not speculative, and it matters more than the two features above. Domain work must not run on the UI thread — the thread that also runs your components and the whole boundary. PTY reads, HTTP, LLM streaming and file I/O belong on Host worker threads.

A worker's only job, as far as the UI is concerned, is to write to a signal. Waking the renderer is internal: the Host requests a frame for you, and repeated requests coalesce into a single render_frame call inside the Compose frame clock. User code never calls a boundary function, and there is no queue between the two sides to fill up.

One consequence worth remembering

Since a handler runs inside the renderer's call into the Host, a frame requested from inside a handler is deferred until that call returns. Re-entering the renderer from a handler is not allowed. Change state and let the frame happen.

The frame budget

The project's performance target is a comparison, not a number in isolation: the same screen written directly in Kotlin and Compose is the baseline, and this stack is allowed at most 10% more frame time than that. A few of the budgets that shape how you write code:

ItemBudget (p99, release)
Host work: handler + diff + batch encoding≤ 0.5 ms for ordinary interaction, ≤ 1 ms for a streaming frame
One boundary call≤ 100 ns on desktop and iOS
Applying a batch in the renderer≤ 0.3 ms per 100 mutations
Input to pixelsSame frame count as the baseline; zero extra frames of latency
Dropped framesZero while streaming 100 tokens/s and scrolling a 10,000-message conversation

Allocation is measured as a trend rather than an absolute: Dioxus allocates internally while diffing and dispatching (99 allocations per click, measured 2026-09-20), and Rust has no GC, so those allocations do not produce pauses. What matters is that repeating the same interaction does not increase the count. Growth means a leak or a cache that stopped working, and is investigated as a bug.
