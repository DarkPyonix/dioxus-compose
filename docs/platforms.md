# 플랫폼별 렌더러 경로

이 저장소는 렌더러를 두 가지로 빌드합니다. 어느 플랫폼이 어느 쪽을 쓰는지, 왜 그런지,
그리고 각각 무엇을 치르는지를 적습니다. 숫자는 전부 계산기 샘플을 실제로 빌드해 잰
것이고, 추정한 값에는 그렇다고 적었습니다.

| | 경로 | 가상 머신 | 상태 |
| --- | --- | --- | --- |
| macOS | Kotlin/Native | 없음 | 동작. 마우스 입력만 미해결 |
| Linux | GraalVM 네이티브 이미지 | 있음 | 동작 |
| Windows | GraalVM 네이티브 이미지 | 있음 | 동작 |
| Web | Kotlin/Wasm | 없음 | 동작 |
| iOS | Kotlin/Native | 없음 | 동작 |

## 무게

전달되는 바이트 전부입니다. 실행 파일과 그 옆에 놓이는 라이브러리를 합쳤습니다.

| | 렌더러 | Skia | 합계 |
| --- | --- | --- | --- |
| macOS, 네이티브 이미지, 시작점 | 71.58 MB | 21.46 MB | **93.1 MB** |
| macOS, 네이티브 이미지, 툴킷 요청 제거 후 | 62.77 MB | 21.46 MB | **84.3 MB** |
| macOS, 네이티브 이미지, 빌더까지 고친 것 | 42.75 MB | 21.46 MB | **64.3 MB** |
| **macOS, Kotlin/Native** | 안에 있음 | 안에 있음 | **28.95 MB** |
| Web, 압축 전 | 11.90 MB | 8.25 MB | 22.25 MB |
| **Web, gzip** | 3.38 MB | 3.17 MB | **6.95 MB** |

Kotlin/Native 쪽은 파일이 하나입니다. 옆에 놓이는 것이 없습니다.

## 빈 창 하나가 쓰는 메모리

계산기 샘플을 열고 12초 뒤에 잰 값입니다. `phys_footprint`는 이 프로세스가 실제로
차지하는 물리 메모리이고, RSS는 공유 매핑까지 포함하므로 프로세스끼리 비교할 값이
아닙니다.

| | 실제 점유 | 힙 | 스레드 |
| --- | --- | --- | --- |
| 툴킷 경로 | 56 MB | | 22 |
| 툴킷 없는 네이티브 이미지 | 39 MB | 13.6 MB | 11 |
| Kotlin/Native | 39 MB | | 10 |
| Calculator.app (애플) | 45 MB | 31.2 MB | 7 |
| TextEdit.app (애플) | 24 MB | | 6 |

애플이 만든 계산기보다 적게 씁니다. 힙은 그 절반 이하입니다. 다만 기능이 같지 않습니다:
애플 쪽은 공학용 모드와 단위 변환과 기록을 들고 있고, 우리 샘플은 사칙연산입니다.

RSS가 더 큰 것은 낭비가 아니라 **우리 코드가 디스크에서 올라온 양**입니다. 애플 앱은
자기 코드가 작고 시스템 프레임워크는 다른 프로세스가 이미 올려둔 것을 공유합니다.
이미지가 줄면 RSS도 그만큼 따라 내려갑니다.

## 무엇이 무게인가

네이티브 이미지 42.75MB를 뜯어보면 이렇습니다.

| | |
| --- | --- |
| 이미지 힙 (문자열과 클래스 메타데이터) | 27.13 MB |
| `java.base` | 5.71 MB |
| `java.desktop` (남은 것) | 1.59 MB |
| GraalVM 자신의 런타임 | 1.24 MB |
| **Compose 전체** | **3.5 MB** |
| **이 저장소의 Kotlin 코드** | **1.0 MB** |

Compose도 Kotlin도 무게가 아닙니다. 둘을 합쳐 5MB 남짓입니다. 나머지 35.7MB는 자바
런타임과, 닫힌 세계로 컴파일할 때 붙는 메타데이터입니다. Kotlin/Native로 가면 그 35.7MB가
사라지고 Skia가 바이너리 안으로 들어옵니다.

## 툴킷을 이미지에서 걷어내기

네이티브 이미지 경로는 창을 자기가 만들기 때문에 툴킷이 필요 없습니다. 그런데도 남아
있었고, 빼는 데 아홉 가지를 시도해 여섯 개가 들었습니다.

| 껐 것 | 값어치 |
| --- | --- |
| 링커가 툴킷 아카이브를 통째로 넣던 것 | 8.8MB의 일부 |
| 툴킷의 입력기와 접근성 다리를 등록하던 feature 둘 | 〃 |
| 도달성 메타데이터에서 툴킷을 이름으로 부르던 항목 34개 | 〃 |
| 이미지를 만드는 동안 툴킷을 깨우던 빌드 플래그 | 〃 |
| 툴킷의 씬만 쓰는 Compose 클래스 넷 | 〃 |
| 툴킷의 레이어만 쓰는 Skia 클래스 넷과 룩앤필 다섯 | 〃 |
| **합계** | **71.58 → 62.77 MB** |

나머지 넷은 한 바이트도 움직이지 못했습니다. 클래스패스에서 툴킷을 언급하는 클래스를
전부 빼기, 툴킷 이벤트를 돌려주는 호출 둘을 대체하기, 툴킷 패키지를 런타임 초기화로
미루기, `--limit-modules`로 모듈에서 빼기. **그 실패가 답이었습니다** — 클래스패스에서는
아무도 요청하지 않고 있었습니다.

요청하는 것은 빌더였습니다. `com.oracle.svm.hosted.jdk.JNIRegistrationAwt`가 플랫폼이
툴킷이 도는 곳인지만 확인하고 무조건 등록합니다. 끌 수 있는 옵션이 없고, 패키지가
`com.oracle.svm`이라 어느 배포판을 쓰든 같습니다. `experiments/no-toolkit-builder/`가 그
클래스를 아무것도 하지 않는 것으로 갈아끼웁니다. 62.77MB가 42.75MB가 됩니다.

## 플랫폼마다 무엇이 발행되어 있는가

Kotlin/Native로 갈 수 있는지는 상류가 그 타깃을 발행하느냐에 달려 있습니다. 직접
확인한 결과입니다.

| | runtime | foundation | ui | material3 | skiko |
| --- | --- | --- | --- | --- | --- |
| macosArm64 | 있음 | 있음 | 있음 | 있음 | 있음 |
| linuxX64 | 있음 | **없음** | **없음** | **없음** | 있음 |
| linuxArm64 | 있음 | **없음** | **없음** | **없음** | 있음 |
| mingwX64 | 있음 | **없음** | **없음** | **없음** | **없음** |

`material3`는 버전에 따라 다릅니다. 1.11.1에는 macOS 네이티브가 없고, 이 저장소가 쓰는
1.11.0-alpha07에는 있습니다. 한 버전만 보고 없다고 판단하면 틀립니다.

**리눅스**는 `runtime`만 있습니다. 그것은 컴포지션 엔진이라 레이아웃도 그리기도 위젯도
없습니다. 흥미로운 것은 skiko가 리눅스 네이티브를 발행한다는 점입니다: 기술적으로 막힌
것이 아니라 Compose가 그 타깃을 빌드하지 않을 뿐입니다.

**윈도우**는 두 겹으로 막혀 있습니다. Kotlin/Native의 윈도우 타깃은 MinGW ABI이고 Skia와
skiko의 윈도우 빌드는 MSVC입니다. C++ ABI가 달라 링크가 성립하지 않고, 애초에
`skiko-mingwx64`가 발행되지도 않습니다. 네이티브 이미지가 유일한 길입니다.

다른 플랫폼의 아티팩트를 가져다 쓸 수는 없습니다. klib은 타깃 정보를 품고 있어 컴파일러가
거부하고, macOS용 `ui`는 AppKit에 묶여 있습니다.

## 리눅스를 네이티브로 가려면

Compose를 소스에서 `linuxX64` 타깃을 켜고 빌드해야 합니다. 분기를 유지하는 포크와는
다릅니다: 타깃을 더하기만 하는 변경이라 상류와 충돌할 일이 거의 없고, 그대로 상류에
보낼 수 있는 모양입니다.

크기는 `macosMain`이 알려줍니다. 플랫폼마다 따로 써야 하는 것이 그 소스셋이고, 데모를
빼면 파일 40개입니다. 그중 25개가량은 데스크톱 동작이라 베끼거나 스텁이면 됩니다
(`Clickable`, `Overscroll`, `Scrollable`, `TouchMode`, `Focusability`, 텍스트 필드
관련 다수, 그리고 이 렌더러가 창을 직접 만들므로 `ComposeWindow`와 `InteropView`).
진짜 구현이 필요한 것은 열 개 남짓입니다: 클립보드, URI 열기, 키 매핑, 커서,
드래그앤드롭, 입력기.

그 열 개가 이 저장소에 이미 있습니다. 네이티브 이미지 경로의 AppKit 창이 같은 일을
하고, X11 창은 `feat/x11-window`에 있습니다.

## macOS Kotlin/Native의 모양

새로 쓴 코드가 거의 없습니다. 인터프리터와 생성된 프로토콜은 iOS 모듈이 이미 하던 대로
`src/shared/`의 심볼릭 링크로 한 벌을 공유하고, 경계도 iOS의 것을 그대로 씁니다 — 그쪽이
어느 플랫폼도 이름 부르지 않고 `@CName` 두 개와 POSIX와 Foundation만 쓰도록 되어 있기
때문입니다.

플랫폼마다 다른 것은 창입니다. Compose는 이 플랫폼용 창을 발행하고 그것은 제대로
그리지만, **그것이 여는 창은 화면 낭독기에게 아무것도 말하지 않습니다.** 타이틀 바의
버튼 셋과 제목만 보이고 응용 프로그램이 그린 모든 컨트롤이 보이지 않습니다. 밖에서
고칠 수 있는 종류가 아닙니다: 낭독기가 원하는 트리는 씬의 플랫폼 컨텍스트를 통해
나오는데, 자기 컨텍스트를 만드는 창은 들어갈 자리를 주지 않습니다.

그래서 `macos/src/MacosWindow.kt`가 씬을 직접 만듭니다. 컨텍스트에 듣는 쪽을 달고,
그리기가 끝난 뒤에 트리를 밀어냅니다. 그 전에 물으면 모든 컨트롤이 빈 사각형을 답하고,
낭독기는 화면 전체가 한구석에 쌓여 있다고 알게 됩니다. 나머지는 Compose의 창이 하는
것과 일부러 가깝게 두었습니다.

접근성을 펼치는 코드 자체는 네이티브 이미지 경로의 것을 그대로 씁니다. 그 파일은 밀어낼
곳을 람다로 받게 되어 있어 어느 플랫폼도 이름 부르지 않습니다.

### 아직 안 되는 것

마우스 입력이 씬에 닿지 않습니다. 키보드는 닿습니다. 둘이 다른 길로 오기 때문입니다:
키보드는 첫 응답자를 따라오고, 마우스는 포인터 아래에 있는 뷰를 따라옵니다. Skia의
레이어가 우리 뷰 위에 자기 뷰를 얹으므로 누름은 그쪽으로 갑니다. `hitTest`를 가져오는
것으로는 아직 해결되지 않았습니다.

## 함정

**렌더러를 다시 빌드해도 응용 프로그램은 예전 것을 링크할 수 있습니다.** 정적
라이브러리를 쓰는 경로는 `DXC_MACOS_NATIVE_LIB`가 가리키는 아카이브를 Cargo에게
감시하라고 말해야 합니다. 그러지 않으면 빌드가 눈 깜짝할 사이에 끝나고, 재는 것은
어제의 바이너리입니다. 이 문서의 숫자 몇 개가 그렇게 한 번씩 틀렸다가 잡혔습니다.

**디버그 빌드의 크기는 배포 크기가 아닙니다.** macOS 디버그 바이너리 57.73MB 중
20.62MB가 심볼과 디버그 정보였습니다. 웹도 같습니다: `web.wasm` 24.12MB의 절반인
12.22MB가 `name` 섹션입니다.
